# Lanes

Компонент resource-timeline. Живе всередині HRM, поки не пройде догфудинг, потім
виноситься в окремий репозиторій як пакет. Назва робоча — перевірити в npm.

## Правило теки

**Нуль імпортів з `@/`.** Ані стилів, ані типів, ані утиліт HRM. Усе прикладне —
аватари, посади, дати найму, права — приходить ззовні через `meta` і слоти.
Це єдине, що робить майбутнє винесення механічним, а не переписуванням.

**Нуль доменних слів.** У теці не має бути ані `employee`, ані `absence`, ані
`holiday`. Якщо доменне поняття просочилось у назву — це спецвипадок HRM,
який у продукті доведеться викорінювати.

**Платний шар не проникає в безкоштовний.** `pro/` імпортує з `core/` і `vue/`;
назад — ніколи. Інакше безкоштовну половину неможливо буде зібрати окремо.

Три перевірки по коду пакета — усі мають бути порожні:

```
grep -rn 'from "@/' --include='*.ts' --include='*.vue' src/lanes/core src/lanes/vue
grep -rni 'employee\|absence\|holiday\|hrm' --include='*.ts' --include='*.vue' src/lanes/core src/lanes/vue
grep -rn 'from "../pro' --include='*.ts' --include='*.vue' src/lanes/core src/lanes/vue
```

`demo/` під ці правила не підпадає: демо на те й демо, що має домен, і саме
воно перевіряє платні плагіни. README теж виключено — він якраз про ці правила
й розповідає.

## Структура

- `core/` — математика без DOM і без Vue: вісь часу, розкладка барів. Тестується vitest.
- `vue/` — компонент, слоти, скрол, теми. Тонкий шар поверх `core/`.
- `pro/` — платні плагіни. Ставляться через проп `plugins`, як будь-які чужі.
- `demo/` — стенди на доменах, відмінних від застосунку. Відкрити: `/dev/lanes`.

Демо існує не для краси: якщо пункт із чеклісту паритету вимагає правки `core/`
або `vue/`, значить, у контракті дірка. Тоді додається **загальний** хук, яким
користуються обидва демо, а не спецвипадок під один застосунок.

## Зафіксовані рішення

| № | Рішення |
|---|---|
| 01 | `core` приймає `plugins: []` з першого дня — точка, куди чіпляється платний шар |
| 02 | Токени теми мають префікс `--rt-*`; це публічний контракт нарівні з props |
| 03 | `end` — ексклюзивний, як у FullCalendar |
| 04 | Компонент контрольований: ресурси, події, діапазон, сорт — ззовні; всередині нуль сховищ |
| 05 | «Настінний» час, зона живе лише у форматері |
| 06 | Ширина слота — CSS-змінна плюс `calc()`, нуль вимірювань у JS |
| 07 | Межа `core` / `vue` — з першого коміту, не «потім розріжемо» |
| 08 | Ліцензійний ключ: код їде разом і працює без ключа, купують за переконанням |
| 09 | Нуль DOM на клітинку: фон сітки — градієнт, стани дня — накладки на всю висоту |
| 10 | Віртуалізація обох осей — безкоштовна й без стелі: платне — поведінка, а не масштаб |

Рішення 08 змінене свідомо: спершу планувались два пакети, але модель ключа
краща для того, як компонент насправді купують — розробник ставить, збирає все,
що йому треба, і платить, коли переконався, що це закриває задачу. Саме так
FullCalendar продав себе цьому застосунку. Тека `pro/` лишається окремою не
заради упаковки, а заради межі: гачки безкоштовні, поведінка платна, і якщо
платний плагін потребує чогось приватного — межу проведено не там.

Рішення 09 і 10 — про те, щоб безкоштовна версія не гальмувала на реальних
розмірах. Ліміт не ставиться ніколи: ані за кількістю рядків, ані за довжиною
осі.

Рішення 10 змінене. Спершу межа проходила по осях: вертикаль безкоштовна,
горизонталь платна. Розбилось воно об власну ж архітектуру — платне в нас це
плагіни, а плагін не може керувати тим, як компонент рендерить клітинки шапки.
Щоб зробити цю віртуалізацію платною, довелося б завести точку розширення
рівня рендеру, тобто новий контракт заради однієї продажної позиції. Заміри до
того ж показали, що позиція слабка: у шапці один елемент на день, рік — це 365,
три роки — 1100. Неприємно, але не смертельно; смертельним був би DOM на
клітинку сітки, а його немає з першого дня (рішення 09).

Тож межа тепер проходить не по осях, а по суті: **швидкість безкоштовна,
платна поведінка**. Так її і пояснювати легше — за неї платять, коли треба
міняти дані, а не коли їх стало багато.

## Платні плагіни

Гачки безкоштовні, поведінка платна. `pro/drag` тримається рівно на трьох
речах із публічного контракту — `hitTest`, `getGeometry`, `getOverlay` — і на
атрибуті `data-item`. Якщо наступному плагіну знадобиться щось приватне, це
дірка в API, а не привід зазирнути в нутрощі.

Плагін нічого не мутує. `drag` рахує, куди елемент переїхав, і віддає це
застосунку через `onMove`; прийняти чи відхилити — його справа. Компонент
керований (рішення 04), і власне сховище в плагіні зламало б це першим же
розходженням між тим, що показано, і тим, що збережено.

Зсув рахується в днях, а не в нових межах з осі: бар міг бути обрізаний краєм
діапазону, і тоді видимий початок — не початок елемента.

Переїзд і розтягування живуть в одному плагіні, бо починаються з того самого
захвату бара: що саме почалось, вирішує місце — край чи середина. Створення
виділенням (`pro/create`) починається з порожнього місця, тож воно окреме й за
захват ні з ким не б'ється — застосунок може дозволити створювати, не
дозволяючи тягати. Жест без обробника не починається взагалі: тягнути бар,
який нікуди не поїде, гірше, ніж не тягнути його зовсім.

Спільне для всіх жестів — `pro/gesture`: натиснули, провезли більше за поріг,
ведемо, відпустили. Жест відрізняється лише чотирма відповідями: чи брати
початок, куди веде вказівник, чи там можна відпустити і що робити далі.

На дотик жест починає утримання, а не рух. Перший рух пальця забирає браузер
під прокрутку, а нам шле `pointercancel` — жест уривається, ще не почавшись.
Поки палець стоїть, прокрутка не почалась, і поки не почалась, її ще можна
відхилити; тож після утримання (`longPress`, типово 400 мс) сторінка до кінця
жесту не їздить. `touch-action: none` на барах вирішило б це одним рядком і
зламало б інше: пальцем не прокрутити таблицю, почавши з бара, — а бар
накриває піврядка. Утримання без руху не робить нічого, як і клік мишею: жест
— це рух, утримання лише відчиняє двері.

Зона краю пальцем теж інша: шість пікселів він накриває цілком і влучає в них
навмання, тож на дотик вона ширша (12 пікселів), але, як і мишею, не більша за
третину бара — середина, з якої бар береться цілком, лишається завжди.

`pro/links` малює стрілки між барами — перший плагін, який малює постійно, а
не під час жесту. Геометрію він бере з контракту, а не з DOM: рядки
віртуалізовані, тож бара, до якого веде стрілка, у розмітці може й не бути —
порахувати його місце можна завжди, а знайти ні. Сигналом до перемальовки є
подія `layout`; вона надсилається і на зміну розкладки, і на зміну геометрії,
бо після зміни ширини дня картинка інша, хоч розкладка та сама.

`pro/history` тримає стек дій, але не знає, як їх відкотити: даними володіє
застосунок, тож він і кладе пару замикань — як скасувати і як повторити. Це не
обмеження, а перевага: у стек лягає будь-яка дія застосунку, не лише наші
жести. Плагін заразом є ручкою — об'єкт, який передають у `plugins`, має ще й
методи стека, тож двох посилань на одне й те саме не треба.

Правила знає застосунок, не плагін. `canMove`, `canResize`, `canCreate`
питаються **на кожному русі**, і заборонена ціль показується перекресленою ще
під час жесту: інакше відпускання мовчки нічого не робить, а це читається як
поламане. Дозвіл і результат рахуються однією функцією — двома шляхами рано чи
пізно вийшло б дозволити одне, а застосувати інше.

`canDrag` — інше питання й інший момент: не «чи можна сюди», а «чи можна взяти
це взагалі», і питається воно один раз, на захваті. Елемент, який таблиця лише
показує — день народження, свято, чужий рядок, — має поводитись як сітка
навколо нього, а не тягнути за вказівником перекресленого привида, якого ніде
не відпустити.

Жест не є кліком, хоч браузер вважає інакше: після відпускання він шле `click`
на спільного предка натискання й відпускання — тобто на рядок. Тому клік, яким
закінчується жест, з'їдається на корені в фазі перехоплення. На корені, а не на
вікні: слухачі вище — «клік поза» самого застосунку, його накладки — мають далі
його бачити. Інакше кожне перетягування закінчувалося б формою, яку застосунок
відкриває на `cell-click`, і найгірше — саме після відхиленого жесту, де
користувач щойно побачив «не можна».

## Токени

Розміри задаються числовими props (`slotWidth`, `barHeight`, `barGap`) — їх має
знати віртуалізація. Оформлення — токенами; це публічний контракт, ламати його
так само дорого, як міняти props.

| Токен | Що фарбує |
|---|---|
| `--rt-surface` | тло сітки й панелі ресурсів |
| `--rt-header-bg` | тло шапки з датами |
| `--rt-text` | основний текст |
| `--rt-muted` | другорядний текст (вихідні, підписи) |
| `--rt-grid-line` | лінії сітки й рамки панелей |
| `--rt-today-bg` | колонка «сьогодні» |
| `--rt-weekend-bg` | колонки вихідних |
| `--rt-bar-bg` / `--rt-bar-text` | бар події |
| `--rt-focus` | обведення бара під фокусом |
| `--rt-ghost-bg` / `--rt-ghost-line` | привид жесту: куди стане бар |
| `--rt-ghost-invalid-bg` / `--rt-ghost-invalid-line` | той самий привид на забороненій цілі |
| `--rt-radius` | заокруглення бара |
| `--rt-pane-gap` | проміжок між панеллю ресурсів і сіткою |

Привида малює платний плагін, а вдягає компонент — і це не дрібниця
розташування. Поки його колір стояв інлайном у плагіні, застосунок не міг
перефарбувати єдине, що видно під час жесту: інлайн не перебити селектором.
Тепер у плагіні лишилась тільки геометрія, а вигляд іде токенами вище; окремий
`className` в опціях плагіна теж працює й нарешті означає те, що обіцяє.

Привид повторює силует бара, а не смугу рядка: прямокутник удвічі вищий за те,
що тягнуть, показує рядок, а не місце. Там, де бара немає — виділення на
порожньому, — береться смуга рядка. Сам бар на час жесту пригасає
(`.rt__bar--dragging`), але не зникає: порівняти «звідки» і «куди» якраз і
треба.

## Мова

Файлів локалей у пакеті немає й не буде: усі вони вже лежать у браузері.
Проп `locale` іде прямо в `Intl` — день підписується числом і скороченим днем
тижня, тиждень діапазоном («12–18 бер», через `formatRange`, який сам знає, як
скорочувати це цією мовою). Без пропа береться мова браузера.

Це не бідніше за півсотні файлів локалей у комплекті конкурента, а рівно
навпаки: підтримуються всі мови, які знає платформа, і жодна не важить нічого.
Кому треба інше — слот `slot-label`, він перекриває підпис цілком.

## Клавіатура й екранні читачі

Табом у таблицю входять один раз: усередині ходять стрілками, бо тридцять
броней інакше означали б тридцять натискань Tab, щоб її проминути. Стрілки
ліворуч-праворуч ведуть від бара до бара в рядку, а не по днях — порожні дні
рахувати ніхто не хоче; вгору-вниз шукається бар, найближчий за часом, бо
рядки між собою не вирівняні. Home і End — краї рядка, Enter і Пробіл — те
саме, що клік. На краю стрілку не забираємо: інакше сторінка перестала б
прокручуватись, і це виглядало б як зависання.

Ім'я бара для читача типово складається з ресурсу й дат («Кімната 101,
2–5 бер»), але застосунок майже завжди знає краще — на те `itemLabel`. Назва
всієї таблиці — проп `label`.

Платні жести теж мають клавіатурний шлях, інакше все, що вміє миша, для
клавіатури не існувало б: Shift зі стрілкою пересуває бар, Alt зі стрілкою
тягне його край. Обидва проходять ті самі `canDrag`, `canMove` і `canResize` —
клавіатура не має бути лазівкою повз правила застосунку.

## Друк

`Ctrl+P` друкує те, що на екрані, і це не недогляд: рядки віртуалізовані, у
розмітці лежать лише видимі. Тому друк — це метод `print()` на компоненті: він
малює всю таблицю, чекає на перемальовку й аж тоді кличе браузер, а після
друку віртуалізація повертається.

У `@media print` токени стають світлими примусово — сіре по темно-сірому в
друку зникає зовсім, — смуга прокрутки ховається, а рядки не розриваються між
аркушами.

## Два режими прокрутки

`scroll: "container"` (типово) — таблиця скролиться всередині висоти, яку задав
застосунок. Годиться для модалок і панелей дашборда.

`scroll: "page"` — таблиця росте на всю висоту, вертикально скролиться сторінка,
а до вікна липнуть шапка (з відступом `stickyOffset` під власний топбар
застосунку) і горизонтальна смуга прокрутки. Фіксована висота — це завжди чиясь
здогадка про чужий екран; тут її не треба.

Шапка навмисно стоїть **над** скролером, а не всередині: будь-який `overflow`
створює власний контекст прокрутки й перехоплює `sticky`, тож усередині вона
липла б до контейнера, а не до сторінки. Горизонтально вісь дат веде
трансформація, а не другий скролер — два справжні скролери довелося б
синхронізувати подіями, і саме там такі компоненти набирають найбільше коду.

Три рівні теми, у порядку зростання пріоритету: світла база → системна темна
(`prefers-color-scheme`, якщо не задано `theme="light"`) → явний `theme="dark"`.
Усі правила мають нульову вагу (`:where`), тож застосунок перевизначає будь-який
токен без `!important`. HRM піде саме цим шляхом: змапить `--rt-*` на `--tb-*`
у своєму блоці `[data-bs-theme]` і `theme` не передаватиме взагалі.

## Публічні частини розмітки

Токенів вистачає на кольори, але не на компонування: рамки панелей, проміжок
між ними, висоту шапки застосунок міняє тільки через селектори. Тому ці класи —
частина контракту нарівні з props, і перейменування будь-якого з них ламає
споживачів:

`.rt` · `.rt__grid` · `.rt__corner` · `.rt__axis` · `.rt__axis-cell` ·
`.rt__axis-day` · `.rt__axis-weekday` · `.rt__axis-range` · `.rt__resources` ·
`.rt__resource` · `.rt__body` · `.rt__column` · `.rt__row` · `.rt__bar` ·
`.rt__background` · `.rt__overlay` · `.rt__ghost`

Модифікатори `--today`, `--weekend`, `--clipped-start`, `--clipped-end`,
`--last`, `--invalid` (на привиді), `--dragging` (на барі, який тягнуть) —
теж. І два атрибути: `data-resource` на рядку, `data-item` на барі —
ними плагін дізнається, що саме схопили.

Розміри округлюються до пристроєвого пікселя, а не до цілого CSS-пікселя: на
масштабі 125% це різні речі. День у 31 CSS-піксель — це 38.75 пристроєвих, тож
кожна четверта лінія лягає на межу, а решта розмиваються; горизонтальна межа
за таких умов зникає зовсім. Дробовий залишок забирає панель ресурсів — там
кілька десятих пікселя не видно, у сітці видно одразу.

Роздільники днів малює змінна `--rt-grid-lines` — один градієнт і для шапки,
і для сітки. Розділяти їх не можна: браузер округлює колонки grid до 1/64
пікселя, похибка накопичується вздовж місяця, і бордери клітинок розходяться
з лініями сітки на видимий піксель.
Усе, що не в цьому списку, вважати внутрішнім.

## Ліцензійний ключ

Рішення 08 у коді: перевірка нічого не вимикає. Платні плагіни без ключа
працюють так само — вона лише каже вголос, чим користуються: раз у консоль і
маленькою позначкою в кутку компонента (`.rt__license`). Позначку малює
платний шар і тільки він: безкоштовна половина про ліцензію не знає нічого,
інакше її не зібрати окремо.

```js
import { setLicense } from "lanes-timeline/pro";
setLicense("LANES.…");
```

Ключ — підписаний payload, а не пароль зі списку: у пакет їде тільки публічний
ключ, тож кейгена не існує навіть у того, хто має весь наш код. Перевірка
офлайн — хто купив компонент, не купував нагляду.

П'ять станів, і три з них мовчазні по-різному. `licensed` — тиша. `unlicensed`,
`invalid`, `outdated` — консоль і позначка, з різним текстом. `unverifiable` —
теж тиша: у незахищеному контексті (звичайний `http`) браузер не дає
`crypto.subtle`, і звинувачувати того, хто заплатив, ми за це не станемо.

Вікно оновлень міряється **датою збірки пакета**, а не годинником клієнта:
куплена версія працює вічно, а випущена після кінця вікна просить поновити.
Годинник переводять, і в обидва боки; дата збірки зашита в бандл (`define` у
`vite.lanes.config.ts`). У вихідниках її немає — власну збірку не ліцензують,
тож у HRM вікно не перевіряється взагалі.

Ключі видаються руками:

```
node scripts/lanes-license.mjs keypair                              # раз на життя
node scripts/lanes-license.mjs sign --licensee "Acme" --until 2027-08-31 --order ord_42
```

Приватний ключ лежить у `~/.lanes/license-private.key` і в репозиторій не
потрапляє. Втратиш — видані ключі лишаться дійсними, але нових не видати:
доведеться міняти `PUBLIC_KEY` у `pro/license.ts`, а це нова версія пакета.

Кожна видача дописує рядок у `~/.lanes/issued.jsonl` — поруч із приватним
ключем, тобто теж поза репозиторієм. Це вся наша база даних, поки справжньої
немає: перевірка офлайн, ключі ми не відкликаємо, і без журналу нічим
відповісти тому, хто свій загубив. Рядок зберігає й сам ключ, тож перевипуск —
це копіювання, а не новий підпис із іншим `id`. Ключі для демонстрацій і тестів
пишуться з `--no-ledger`: журнал відповідає на питання «кому ми що продали», а
не «що ми колись підписували».

Тести не мають справжнього ключа й не повинні: `verifyLicense` бере публічний
ключ параметром, і тест генерує власну пару. Інакше перевірити перевірку можна
було б лише поклавши приватний ключ у репозиторій.

## Пакування

Тека вже пакет: `package.json` лежить тут, і `npm publish ./src/lanes` зібрав
би тарбол просто звідси. Виносити в окремий репозиторій поки нема за чим —
доки HRM живиться вихідниками через `@/lanes/...`, розбіжність між тим, що
працює, і тим, що зібрано, помітна того ж дня.

```
npm run lanes:check   # три правила межі теки, але виконувані
npm run lanes:build   # межа → збірка → типи → перевірка пакета
npm run lanes:pack    # те саме плюс тарбол, щоб зазирнути всередину
```

Дві точки входу, а не одна: `.` — компонент і вісь, `./pro` — плагіни. Хто не
імпортує платного, той його й не збирає: `24 кБ` проти `18 кБ` окремо, спільна
в них лише арифметика дат. Стилі — окремим файлом (`./style.css`), бо
бібліотека не має права вирішувати за застосунок, коли їх вантажити:

```js
import { Timeline } from "lanes-timeline";
import { drag } from "lanes-timeline/pro";
import "lanes-timeline/style.css";
```

`vue` — peer-залежність: другий примірник у збірці зламав би реактивність.

Збірка успішна не тоді, коли rollup не впав. Перша ж збірка мовчки поклала в
пакет `public/` застосунку — фавікон, іконки, service worker; тому
`lanes-verify` перевіряє, що кожен шлях із `exports` існує, а точки входу
справді імпортуються й віддають обіцяне.

**Чотири речі перед першою публікацією — за користувачем, не за мною:**

1. Назва. `lanes` і `vue-lanes` в npm зайняті; вільні `lanesjs`,
   `lanes-timeline` (стоїть зараз), `lanes-vue`, `timeline-lanes`.
2. Ліцензія. Зараз `UNLICENSED` — чесно, поки тексту немає. Рішення 08 каже
   «код їде разом і працює без ключа», а це не MIT і не пропрієтарщина без
   вихідників; текст має бути написаний до публікації, не після.
3. Куди слати по ліцензію. У повідомленні зараз немає адреси — писати
   неіснуючий сайт я не став. З'явиться домен — рядок один, у `NOTICE`.
4. README. Цей файл — внутрішній: правила межі, рішення, чому платне платне.
   А npm кладе `README.md` з кореня пакета в тарбол **завжди**, хоч би що
   стояло в `files`. Отже, або тут з'явиться README для тих, хто ставить
   пакет, а цей поїде під іншим ім'ям, або перша ж публікація віддасть наші
   внутрішні міркування разом із кодом.
